# PostgreSQL Evidence Adapter: Operations and Security Notes

## Scope

`agentguard-evidence-postgres` is the first durable reference implementation of
`AppendOnlyEvidenceStore`. It is not a production deployment profile, compliance
certification, or proof against a compromised database administrator.

Apply `migrations/0001_evidence_store.sql` before connecting the adapter.

## Transaction and concurrency model

Each append verifies the sealed event before opening a transaction. The adapter
creates the stream-head row if absent, locks that row with `SELECT ... FOR UPDATE`,
then checks idempotency, expected sequence, and predecessor hash. It inserts the
canonical serialized event bytes and advances the stream head in the same
transaction. A successful return occurs only after COMMIT succeeds.

Multiple adapter instances coordinate through PostgreSQL row locks. The local
client mutex only serializes operations using one adapter instance; it is not
the cross-process correctness mechanism.

An exact retry (same tenant, stream, event ID, and serialized bytes) succeeds
without adding a second row. Reusing an event ID with different bytes, sequence
gaps, stale predecessors, and uniqueness conflicts fail closed.

Reads use a repeatable-read, read-only transaction, verify event identity and
the complete hash chain, and compare the resulting tail with the separately
stored stream head. This detects missing or truncated rows when the head row
remains intact. It does not detect a privileged attacker rewriting both tables.

## Database role separation

Use separate migration-owner and runtime application roles. The runtime role
needs SELECT and INSERT on the event table and SELECT and the narrowly required
INSERT/UPDATE privileges on the stream-head table. It must not receive UPDATE
or DELETE on `agentguard_evidence_events`, nor ownership or DDL privileges.

Example after creating the tables as the migration owner (replace role names
with deployment-specific identities):

```sql
REVOKE ALL ON agentguard_evidence_events FROM PUBLIC;
REVOKE ALL ON agentguard_evidence_stream_heads FROM PUBLIC;
GRANT SELECT, INSERT ON agentguard_evidence_events TO agentguard_runtime;
GRANT SELECT, INSERT, UPDATE ON agentguard_evidence_stream_heads TO agentguard_runtime;
REVOKE UPDATE, DELETE, TRUNCATE ON agentguard_evidence_events FROM agentguard_runtime;
```

Do not run the runtime application as the migration owner or table owner.
Review grants after every migration. Tenant IDs must come from authenticated
server-side identity, never from an untrusted request body alone. Add and test
row-level security policies in deployments where database-enforced tenant
isolation is required.

## Transport and durability

The convenience `connect` constructor currently uses PostgreSQL `NoTls` and is
intended for local development and CI only. For networked deployments, construct
a TLS-configured `postgres::Client` using the deployment's trusted CA and pass
it through `PostgresEvidenceStore::from_client`. Never send database credentials
or evidence over an untrusted network without TLS.

Configure PostgreSQL durability according to the threat model. A successful
commit is only as durable as the database's WAL, storage, replication, and
backup configuration. Document and test backup/restore, point-in-time recovery,
and restore-time chain verification. A database superuser can still rewrite
evidence; independently retained signed checkpoints are a separate future gate.

## Current limitations

- Synchronous single-client connection per adapter instance; use multiple instances for concurrent callers.
- No built-in connection pool, TLS connector, migration runner, RLS policy, or checkpoint signer.
- No multi-region consensus or external side-effect authorization.
- Commit connection loss can leave the client uncertain whether COMMIT reached the server. Callers must reconcile by reading the event ID and exact payload before retrying; never infer failure or success from a transport error alone.
