# G4.4 — Durable Evidence Storage Adapter Contract

**Status:** Design baseline; implementation blocked on adapter/backend selection  
**Depends on:** G4.3 evidence event schema, sealing, and stream verification  
**Security posture:** No production-readiness claim

## 1. Objective

Turn the G4.3 append-only evidence contract into a verifiable durable persistence boundary. The adapter must preserve event integrity under concurrent writers, retries, process crashes, partial failures, and tenant isolation failures.

This document defines backend-independent requirements. It does not select a database, claim that a storage implementation exists, or authorize production use.

## 2. Non-negotiable invariants

1. **Append-only:** committed event payloads and ordering metadata cannot be updated or deleted through the application adapter.
2. **Atomic append:** an append either commits the event and advances the stream head together, or commits neither.
3. **Contiguous sequence:** the only acceptable next sequence is the committed stream head sequence plus one.
4. **Predecessor binding:** the event's previous hash must equal the committed stream head hash; the first event must reference the G4.3 genesis hash.
5. **Integrity before persistence:** the adapter verifies the event hash and schema before attempting commit. It must not trust caller-supplied hash fields.
6. **Idempotency:** retries with the same event identity and identical canonical event bytes return an idempotent success; reuse of an event identity with different bytes is a conflict.
7. **Tenant isolation:** tenant identity is derived from an authenticated authorization context at the adapter boundary, not trusted solely from an event payload or caller-provided query parameter.
8. **Fail closed:** uncertain commit outcome, unavailable consistency guarantees, malformed event, sequence conflict, or tenant mismatch must never be reported as successful persistence.
9. **Durability acknowledgement:** success is returned only after the backend's documented durable-commit boundary has been reached.
10. **No false execution claims:** evidence persistence proves that a record was committed, not that an external side effect actually occurred.

## 3. Logical storage model

The reference logical model has two records:

### Evidence stream head
- tenant_id
- stream_id
- last_sequence
- last_event_hash
- updated_at

The stream head is concurrency-control metadata. It is mutable only inside the same atomic transaction that appends the next immutable event.

### Evidence event
- tenant_id
- stream_id
- sequence
- event_id
- event_hash
- previous_event_hash
- canonical event payload
- committed_at (storage metadata; not part of the event hash)

Required uniqueness constraints:
- (tenant_id, stream_id, sequence)
- (tenant_id, stream_id, event_id)

Required lookup index: (tenant_id, stream_id, sequence) in ascending order.

The application-facing interface must not expose update or delete operations for committed events. Administrative retention or legal deletion, if ever required, must be a separately governed capability with explicit policy and audit evidence; it must not be disguised as ordinary append API behavior.

## 4. Atomic append algorithm

An adapter implementation must provide an equivalent transactionally serialized operation:

1. Authenticate and authorize the caller for the target tenant and stream.
2. Validate the typed event and call the G4.3 event verifier.
3. Begin a transaction with isolation/locking semantics sufficient to serialize writers for the same (tenant_id, stream_id).
4. Lock or conditionally compare the stream-head row.
5. Resolve idempotency: identical event identity and canonical bytes is an idempotent success; same identity with different bytes is a conflict.
6. Require sequence = last_sequence + 1 and previous_event_hash = last_event_hash; for a new stream require sequence 1 and the genesis hash.
7. Insert the immutable event and update the stream head in the same transaction.
8. Commit durably.
9. Return success only after commit acknowledgement.

A uniqueness violation or compare-and-swap conflict must be surfaced as a typed conflict, not silently retried with a modified event. A bounded internal retry is permissible only when the adapter re-reads the committed head and the caller's event is still exactly the next valid event; otherwise the caller must reseal a new event from the current head.

## 5. Read and verification behavior

- read_stream must return one consistent ordered snapshot, scoped to the authenticated tenant.
- The adapter must not return a partial stream as a successful complete read.
- The caller or adapter must run verify_stream on the returned sequence before treating it as integrity-verified.
- A separate head/checkpoint read must expose the current committed sequence and hash so consumers can detect a stale or truncated export.
- A stream hash chain alone cannot detect tail truncation or full rewrite. Production integrity claims require independently retained signed checkpoints or equivalent externally anchored commitments. Checkpoint signing and key lifecycle are out of scope for G4.4 unless separately approved.

## 6. Failure and recovery contract

The adapter must distinguish at least:
- invalid event / failed hash verification;
- unauthorized tenant or stream access;
- sequence or predecessor conflict;
- idempotency conflict;
- transient backend unavailability;
- transaction aborted;
- commit outcome unknown;
- durable commit confirmed.

If the connection drops during commit and the outcome is unknown, the adapter must not claim failure or success without reconciliation. It must query by tenant-scoped event identity and compare the complete canonical bytes/hash before deciding whether the request committed.

After process restart, recovery must reconcile the stream head against the highest committed event. A mismatch is a corruption condition and must fail closed; the adapter must not silently repair or rewrite evidence.

## 7. Required conformance tests

### Correctness
- first event from genesis;
- sequential append and full ordered read;
- stable idempotent retry of identical event;
- rejection of same event ID with different payload;
- rejection of duplicate sequence;
- rejection of skipped sequence and wrong predecessor;
- rejection of malformed/tampered event hash;
- tenant and stream isolation on both append and read.

### Concurrency
- many concurrent writers to one stream produce exactly one committed event per sequence;
- two writers attempting the same next sequence cannot both succeed;
- writers to different streams do not corrupt each other's heads;
- duplicate retries under concurrency remain idempotent.

### Crash and uncertainty
- crash before transaction commit leaves neither event nor head advancement;
- crash after confirmed commit preserves both event and head;
- simulated lost commit acknowledgement is reconciled by event identity and exact bytes;
- restart detects event/head inconsistency and fails closed.

### Durability and operations
- documented backend durability settings and limitations;
- backup/restore test with post-restore full stream verification;
- migration test from an empty schema;
- no application role permission to update/delete committed event rows;
- metrics and logs do not expose raw secrets or full sensitive payloads.

## 8. Backend selection gate

Before implementing the production adapter, record an Architecture Decision Record comparing candidate backends against:
- atomic conditional append and per-stream serialization;
- durable commit semantics and documented failure modes;
- tenant isolation and database role/RLS capabilities;
- operational complexity for a solo maintainer;
- local development and CI reproducibility;
- backup, restore, migration, and recovery support;
- licensing and long-term portability.

The first implementation must be one reference adapter behind a narrow trait. Do not introduce multiple database backends in the same milestone.

## 9. Explicit exclusions

G4.4 does not implement or authorize permit signing or consumption, runtime interception, external side-effect delivery, signed checkpoint/key management, multi-region consensus, retention/deletion administration, or production deployment.

The runtime must continue to fail closed and must not issue an ALLOW permit on the assumption that the storage contract alone guarantees durable evidence.

## 10. Exit criteria

G4.4 can be marked implementation-complete only when:
1. A backend ADR is approved and recorded.
2. A concrete adapter implements the G4.3 storage interface with authenticated tenant scoping.
3. Database constraints and transaction logic enforce the invariants above.
4. All correctness, concurrency, crash/recovery, and tenant-isolation tests pass in CI.
5. The adapter's durability assumptions and known limitations are documented.
6. A reviewer verifies the implementation and tests; no production-readiness claim is made solely from passing unit tests.
