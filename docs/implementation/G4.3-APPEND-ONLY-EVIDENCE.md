# G4.3 — Append-Only Evidence and Hash-Chain Verification

**Status:** Implementation in progress  
**Normative sources:** ADR-0004, ADR-0003, EVIDENCE-FORMAT v0.1.0

## Objective

Implement deterministic event sealing and offline verification without duplicating canonicalization or implying that a hash chain is durable storage.

## Implemented contract

- agentguard-evidence depends on agentguard-canonical and uses only the closed Event digest domain.
- Event hashes cover the complete typed event payload and previous_event_hash; event_hash is excluded from its own preimage.
- The canonical crate validates the serialized preimage under the constrained AgentGuard JCS profile before SHA-256.
- Genesis predecessor is 32 zero bytes encoded as 64 lowercase hexadecimal characters.
- A stream verifier checks sequence continuity from 1, tenant and stream identity consistency, predecessor linkage, record schema constraints, and every event digest.
- Event types and decision outcomes are closed enums. Unknown JSON fields are rejected during typed deserialization.
- Corrections are new events and may identify correction_of_event_id; prior records are never modified by these primitives.
- Validation errors are stable categories and do not echo evidence payload contents.
- The public AppendOnlyEvidenceStore contract exposes append and complete ordered stream reads only. Implementations must verify the event and atomically compare the tenant/stream key, next sequence, and predecessor against the committed tail; reject duplicate event IDs; commit durably; and expose no update/delete operations.

## Security limits and explicit non-claims

- Hash-chain validity proves internal byte integrity relative to the supplied first event; it does not prove truth, completeness before ingestion, durable persistence, or that an external side effect occurred.
- Deletion of a middle event is detected by sequence/link checks. Tail truncation and full-stream rewrite cannot be detected without an independently retained signed checkpoint.
- seal_event is a pure function. It does not allocate sequence numbers, serialize concurrent writers, or persist data.
- No production storage adapter is implemented in this slice. The trait contract is not proof of linearizability or durability; an adapter must fail closed on storage uncertainty and must be tested under concurrent writers, process crashes, and recovery before production use.
- The runtime MUST NOT issue an ALLOW permit until the corresponding decision evidence has been durably committed. This crate alone does not establish that invariant.
- Timestamp validation enforces the UTC RFC 3339 shape, calendar day bounds (including leap years), clock ranges, optional fractional seconds, and a Z suffix. Leap-second values are syntactically accepted; authoritative time provenance remains the trusted runtime's responsibility.
- Hashes are not signatures, and independent signed checkpoints remain deferred.

## Required verification

- Unit tests cover deterministic sealing with a fixed independently computed event digest vector (`b87836865744006e46c8e3911d7b3f35ce188e6f38aa9df82c559edba22e12a8`), successful stream verification, payload/hash/predecessor tampering, deletion, reordering, duplication, tenant/stream mixing, malformed hashes, invalid timestamps, genesis/sequence invariants, invalid draft fields, and strict event decoding.
- Workspace formatting, Clippy, and all tests must pass.
- A later persistence slice must add concurrent multi-writer and crash/recovery tests against the selected durable backend before claiming production readiness.
