# G4.1 — Deterministic Policy Core Implementation

**Status:** In progress — implementation slice only  
**Baseline:** G1 v0.1.0, G2 v0.1.0, G3 v0.1.0  
**Scope:** Pure policy combining and exact selector/predicate evaluation in Rust.

## 1. Scope of this slice

This increment implements the pure, deterministic policy-combining boundary in `agentguard-policy`:
- exact action, principal/agent, and resource selectors;
- typed condition values without floating-point numbers;
- AND semantics across conditions;
- deny-overrides, then approval-required, then allow, then default deny;
- stable reason codes and sorted/deduplicated approval profile IDs;
- fail-closed handling for unsupported policy schema and malformed policy structure.

The evaluator has no I/O, ambient clock, randomness, network access, LLM dependency, signing key, or evidence-store access.

## 2. Explicit non-goals

This slice does not implement or claim:
- authentication or identity assertion verification;
- context source trust, provenance, or freshness verification;
- policy signature verification or canonical policy digests;
- approval recording, quorum authentication, or re-evaluation lifecycle;
- permit signing, G3 attestation, revocation, or PermitEnvelopeV2;
- durable evidence, atomic permit consumption, side effects, or production enforcement;
- wire APIs, MCP integration, TypeScript/Python SDKs, or deployment.

The caller must validate identity assertions, policy authenticity, context provenance/freshness, and request schema before invoking this pure evaluator. A future runtime API must make this boundary explicit and impossible to bypass accidentally.

## 3. Deterministic semantics

For a structurally valid policy bundle:
1. Match rules using exact identifiers only; wildcard/pattern matching is not supported.
2. A rule matches only when its subject/resource selectors match and every condition evaluates true.
3. Any matching DENY returns DENY.
4. Otherwise, any matching REQUIRE_APPROVAL returns REQUIRE_APPROVAL with all distinct matching profile IDs.
5. Otherwise, one or more matching ALLOW rules return ALLOW.
6. No matching rule returns DENY.

Rule ordering and map insertion order must not change the decision. No implicit type coercion is permitted. Floating-point values are not representable in the evaluator's value model.

## 4. Verification required for this slice

- allow and default-deny behavior;
- deny-overrides regardless of rule order;
- approval-required overrides allow;
- deterministic sorted approval profile output;
- unsupported schema and duplicate rule IDs fail closed;
- exact selectors;
- typed numeric condition comparison and incompatible-type rejection;
- empty/invalid action selector and invalid approval-profile configuration fail closed.

CI must run `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, and `cargo test --workspace --all-targets`. No check is considered passed until GitHub reports success.

## 5. Security boundary and remaining work

A DENY from this evaluator is not a cryptographic proof or a complete authorization lifecycle. Production enablement remains blocked until upstream trust validation, deterministic canonicalization, append-only durable evidence, approval lifecycle, permit signing and verification, G3 attestation/revocation, linearizable single-use consumption, adapter review, and independent external security review are implemented and verified.
