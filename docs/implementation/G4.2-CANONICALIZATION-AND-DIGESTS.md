# G4.2 — Canonicalization and Domain-Separated Digests

**Status:** Implementation in progress — conformance corpus added; CI and independent review pending  
**Parent baseline:** G1 v0.1.0, G2 v0.1.0, G3 v0.1.0, G4.1 merged  
**Normative source:** ADR-0003; RFC 8785 (JCS)

## 1. Objective

Implement one canonical byte boundary for every security-relevant JSON object hashed or signed by AgentGuard. Rust runtime and future TypeScript/Python SDKs MUST produce byte-identical canonical output and SHA-256 digests for identical validated inputs.

This slice is a prerequisite for G4.3 evidence hashing and for later policy, permit, attestation, and revocation bindings.

## 2. Canonicalization contract

1. Canonical JSON MUST follow the RFC 8785 (JCS) serialization rules for the supported AgentGuard v1 value domain: recursive object-member ordering by UTF-16 code units, compatible string/primitive serialization, and preservation of array order. This is a constrained security profile, not a general-purpose implementation of every RFC 8785 numeric case.
2. Input MUST be UTF-8 JSON. Invalid UTF-8, malformed JSON, invalid Unicode strings, and lone surrogate escapes MUST be rejected.
3. Duplicate object member names MUST be rejected before any map/value representation can collapse them. Detection is recursive and compares decoded member names, so escaped-equivalent names (for example, `"a"` and `"\u0061"`) are duplicates.
4. No Unicode normalization, case folding, locale transformation, or application-level string rewriting is permitted.
5. Security-relevant AgentGuard v1 payloads MUST contain no floating-point numbers, except that any negative-zero JSON number representation (for example `-0`, `-0.0`, or `-0e0`) MUST canonicalize to the integer token `0` as required by RFC 8785. Positive zero written with a fractional or exponent form (for example `0.0`) remains rejected by this constrained profile. Integer values MUST be in the interoperable safe range `[-(2^53-1), +(2^53-1)]`. Larger integers, exact decimals, monetary values, and identifiers requiring more precision MUST use schema-defined strings with explicit semantic type and scale.
6. Unknown fields MUST be rejected by the relevant versioned security schema unless explicitly defined as extension data. Canonicalization itself does not replace schema validation.
7. Canonicalization MUST be deterministic, pure, bounded by a maximum raw input size of 1 MiB and a maximum nesting depth of 128 levels, and must not log or echo sensitive payload contents on error. Implementations MUST expose these limits as stable profile constants and map limit violations to `InputTooLarge` or `NestingLimitExceeded`.

The implementation MUST NOT use ordinary `serde_json::to_string`, sorted-key JSON, or a serializer whose behavior differs from the AgentGuard v1 profile as a substitute for the specified canonicalization contract. String escaping and key ordering MUST be covered by byte-exact conformance vectors.

## 3. Public API and ownership

Create a small dedicated canonicalization crate (proposed name: `agentguard-canonical`) that owns:
- strict raw-byte parsing and validation;
- duplicate-member detection;
- canonical byte generation;
- domain-separated SHA-256 digest generation;
- stable, non-sensitive error categories.

Callers MUST pass raw bytes at untrusted JSON boundaries. An already-materialized map or `serde_json::Value` is not an acceptable substitute where duplicate-key evidence may already have been lost.

The canonical crate MUST NOT depend on runtime, policy, evidence, or enforcement crates. Higher-level crates may depend on it. The canonical crate MUST NOT perform authorization decisions, I/O, network access, key management, signing, or persistence.

## 4. Domain-separated digest contract

The preimage is exactly:

`UTF8(domain_separator_including_NUL) || canonical_json_bytes`

SHA-256 is applied once to the complete preimage. The output encoding is lowercase hexadecimal, exactly 64 ASCII characters, without a prefix.

Version 1 domain separators are fixed byte strings:

| Domain | Exact UTF-8 bytes |
|---|---|
| REQUEST | `AIVO-AGENTGUARD-REQUEST-V1\0` |
| ACTION | `AIVO-AGENTGUARD-ACTION-V1\0` |
| POLICY | `AIVO-AGENTGUARD-POLICY-V1\0` |
| PERMIT | `AIVO-AGENTGUARD-PERMIT-V1\0` |
| EVENT | `AIVO-AGENTGUARD-EVENT-V1\0` |

The NUL byte is part of the preimage and MUST NOT be omitted, escaped as two printable characters, or appended after hashing. Domain identifiers are closed enums, not caller-provided strings. A digest from one domain MUST NOT be accepted as a digest from another.

## 5. Golden-vector corpus

Each vector MUST include:
- stable vector ID and schema/profile version;
- domain enum;
- raw input bytes (including whitespace and key-order variants);
- expected canonical UTF-8 bytes;
- expected full preimage bytes or an unambiguous hex representation;
- expected SHA-256 lowercase hex;
- expected accept/reject result and stable error category.

Required positive coverage:
- empty object and empty array;
- nested objects and arrays, preserving array order;
- recursive key sorting;
- UTF-16 key ordering, including non-BMP characters;
- quote, backslash, slash, and C0 control escaping;
- Unicode preservation without normalization;
- integer boundaries at `±(2^53-1)`;
- all five digest domains;
- equivalent raw JSON with different whitespace and object-key order yielding identical canonical bytes and digest.

Required negative coverage:
- duplicate keys at root and nested levels;
- escaped-equivalent duplicate keys;
- invalid UTF-8 and malformed JSON;
- lone high/low surrogate escapes;
- floating-point values in the AgentGuard v1 security profile;
- integers outside the safe range;
- schema-level unknown fields and unsupported profile versions are rejected by the consuming versioned schema validator, not by this low-level canonicalization crate;
- input-size and nesting-depth limit violations.

The repository-owned corpus is `crates/agentguard-canonical/tests/vectors/canonicalization-v1.json`; it records exact canonical bytes or stable rejection categories for the constrained AgentGuard profile. The RFC 8785 Appendix B numeric serialization examples that require general IEEE-754 floating-point serialization are outside this profile and MUST NOT be presented as supported JCS numeric vectors; floating-point forms are rejected, with the RFC-required negative-zero normalization retained. Safe-integer boundary cases and the applicable non-floating serialization rules are covered. Expected outputs are fixed fixture values, not computed by the implementation under test. The separate `domain-digests-v1.json` corpus fixes preimage and SHA-256 outputs for all five domains.

## 6. Verification and release gates

- Unit tests for parser, duplicate detection, Unicode, numeric restrictions, canonical bytes, and digest domains.
- Golden-vector tests compare exact bytes, not only parsed JSON equality.
- Property-style generated tests: canonicalization is idempotent; object insertion order does not affect output; array order does affect output. These deterministic generated cases supplement, but do not replace, a dedicated coverage-guided fuzzing campaign.
- Cross-implementation parity fixtures are reserved for TypeScript and Python SDK milestones; the corpus format is language-neutral from day one.
- A `cargo-fuzz` target exists at `fuzz/fuzz_targets/canonicalize_json.rs` and exercises the raw-byte boundary, including recursive duplicate detection. Before acceptance, execute and record a bounded fuzz campaign (for example `cargo +nightly fuzz run canonicalize_json -- -max_total_time=300`) and triage any crash, timeout, or sanitizer finding. The harness's existence alone is not evidence that fuzzing has passed.
- `cargo fmt --all -- --check`, strict workspace Clippy, and full workspace tests MUST pass in CI.
- No G4.3 event hash-chain implementation may fork or duplicate canonicalization logic.

## 7. Explicit non-goals

This slice does not implement evidence persistence, event sequencing, hash-chain verification, signatures, policy evaluation, approval lifecycle, permit issuance, attestation, revocation, or atomic consumption.

## 8. Acceptance

G4.2 is complete only when the canonical crate, strict raw-input boundary, all five domain digest functions, frozen golden vectors, negative tests, and CI verification are merged. Documentation-only completion is not sufficient.
